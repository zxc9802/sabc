# Finalize Job Polling Design

## Goal

Replace the long-lived `/api/finalize` SSE request with an in-process background
job and short polling requests. Closing the page connection or passing through an
iframe/reverse proxy must not cancel an already-started final analysis.

## Scope

- Change only the finalization flow that currently calls `/api/finalize`.
- Preserve the existing research, analysis, scoring, persistence, and report
  navigation behavior.
- Keep jobs in the running Next.js server process. A server restart may lose
  active and completed jobs.
- Do not add Redis, SQLite, authentication, distributed locking, or a worker
  service in this iteration.

## Architecture

`POST /api/finalize-jobs` validates the existing finalization request, creates a
job, starts the current finalization pipeline without using the browser request's
abort signal, and immediately returns HTTP 202 with the job ID.

`GET /api/finalize-jobs/[jobId]` returns a snapshot of the job. The snapshot
contains its state, current finalization stage, optional research plan and
research snapshot, optional assessment, or a safe terminal error.

The client polls the GET endpoint every two seconds. It applies newly observed
research and assessment data through the existing reducer and repository paths.
Polling continues across transient GET failures and stops on completion,
terminal failure, explicit user cancellation, or component disposal. Explicit
client cancellation stops polling but does not cancel the background job.

## Job Model

Each job contains:

- `id`: a random UUID generated by the server.
- `state`: `queued`, `running`, `completed`, or `failed`.
- `stage`: the existing `FinalizeStage` when execution has begun.
- `researchQueries`: the latest planned query list, if available.
- `researchSnapshot`: the latest completed research snapshot, if available.
- `assessment`: the final `AnalyzeProjectResponse`, if available.
- `error`: the existing safe code, message, and retryable flag on failure.
- `createdAt` and `updatedAt`: ISO timestamps.

Snapshots returned to clients are cloned so callers cannot mutate registry
state.

## Lifecycle and Cleanup

The registry creates the job before starting asynchronous work, ensuring the
POST response never waits for AI completion. Terminal jobs are retained for 30
minutes. Cleanup runs opportunistically during create and get operations; no
per-job timers are created.

Unknown or expired IDs return HTTP 404 with code `job_not_found`. A server
restart has the same observable result and the UI tells the user to start the
final analysis again.

## Idempotency

The client stores the active job ID in the current assessment hook while the
page is mounted. Repeated clicks during a busy phase remain blocked by the
existing reducer. This iteration does not add cross-refresh or cross-tab
idempotency because jobs are intentionally process-local.

## Error Handling

The background pipeline uses the existing safe provider, research, schema, and
internal error mapping. Errors are recorded in the job instead of being sent on
an SSE stream.

A transient polling network failure is retried after two seconds. A valid
terminal job error uses the existing retry action. A missing job is terminal
for that client attempt and prompts a new finalization.

## Testing

- Unit-test registry creation, state/event updates, immutable snapshots,
  terminal failure, expiration, and missing IDs.
- Route-test immediate 202 creation, GET snapshots, invalid input, and unknown
  jobs.
- Hook-test polling through research, analysis, completion, terminal failure,
  and a transient network failure.
- Keep the existing finalization pipeline tests to prove research and scoring
  behavior remain unchanged.
- Run the focused tests, complete Vitest suite, ESLint, and production build.
