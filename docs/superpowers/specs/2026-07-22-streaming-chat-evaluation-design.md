# SABC 流式尽调聊天模式设计

- 状态：设计已确认，待实施计划
- 日期：2026-07-22
- 目标目录：`D:\SABC智能体新`
- 默认问答深度：中

## 1. 背景

当前工作区虽然会保存用户消息和 AI 消息，但一次分析必须等待完整 JSON 响应后才显示结果；AI 回复由前端模板拼接，当前追问又被放在聊天记录之外的独立表单中。用户因此看到的是“提交表单—等待评分—填写下一张表单”，而不是连续对话。模型请求失败时，页面还会直接暴露 `502` 或 `SCHEMA_ERROR`，用户无法从聊天语境中理解失败原因并自然继续。

本次改造把中间区域变成真正的尽调聊天：用户每次回答后，AI 先说明理解了什么、这条信息能否构成证据、为什么当前评分可以或不可以变化，然后只提出一个最关键的后续问题。AI 生成的文字通过真实模型流立即显示，右侧评分仍由确定性规则计算并逐轮更新。

## 2. 目标与非目标

### 目标

- 中间区域成为连续、可恢复的聊天记录，不再使用独立的“当前唯一追问”表单。
- 模型生成一段，页面立即显示一段，不等待完整回复结束。
- AI 每轮都回应用户刚才说了什么，解释证据影响，并只追问一个问题。
- 问答深度支持低、中、高三档，默认中档，可在对话中切换。
- 取消总轮数上限，直到证据充分、用户主动结束或用户选择跳过。
- 右侧评分在每轮评估完成后更新，并突出本轮发生变化的维度。
- 分数、等级、置信度和下一问选择继续受程序规则约束，模型不得自行决定。
- 流式生成中止或失败后，已完成的评估不丢失，用户可以继续交流。

### 非目标

- 不改动七维评分权重、等级阈值、证据上限和否决规则。
- 不重做左侧案卷索引、项目对比和报告功能。
- 不增加账号、云同步、附件上传或服务端业务数据存储。
- 不把 API Key、模型原始响应或思维过程暴露给浏览器。
- 不加入多问题并发访谈；每轮仍然只问一个问题。

## 3. 已确认的产品决策

1. 右侧评分每轮更新，不等到访谈结束才显示。
2. 不设置固定的六轮上限。
3. 回答模糊、矛盾或缺少证据时，AI 可以围绕同一主题继续深挖。
4. 流式输出必须来自真实模型生成，而不是完整响应返回后的逐字动画。
5. 问答深度分为低、中、高，默认使用中档。
6. 采用“先结构化评估，再流式组织回复”的两阶段方案，以保证解释、评分和下一问一致。

## 4. 用户体验

### 4.1 中间聊天区

- 用户消息靠右，AI 消息靠左，按时间形成一条连续的证据访谈记录。
- AI 回复使用自然段落，不强制堆叠卡片。内容语义依次包含：
  1. 对本轮回答的理解和确认；
  2. 新信息对证据与评分的影响；
  3. 仍然缺少或不能验证的部分及原因；
  4. 程序选定的一个后续问题。
- 流式生成时保留可见光标和“正在组织回复”状态，新增片段追加到当前 AI 消息中。
- 原来的独立追问表单移除；AI 回复最后一句就是当前问题，用户统一在底部输入框回答。
- 快捷回答仍可保留，但点击只负责填入输入框，用户可以继续编辑后再发送。
- 输入框固定在聊天区底部；发送期间防止重复提交。
- 模型开始输出后显示“停止生成”。停止后保留已经完成的评分，并提供可继续输入的状态。
- 新消息到达时自动跟随到底部；用户主动向上查看历史后，不强制抢夺滚动位置。

### 4.2 深度选择

聊天标题区增加“问答深度”分段选择器：低 / 中 / 高。切换值从下一轮开始生效，并保存在当前项目中；没有该字段的旧项目按“中”处理。

- **低**：快速覆盖七个维度。同一证据点通常只追加一层核实，仍无法确认时记为未验证并转向其他高价值缺口。
- **中**：对影响评分的关键说法连续追问两到三层，通常追到数量、金额、时间、对象、来源或验证方式。
- **高**：按尽调方式持续核实。遇到模糊、矛盾或只有结论没有依据的说法时，继续追问计算过程、来源和反例，直到证据可验证、用户明确无法提供或主动跳过。

深度限制的是同一证据链的追问强度，不重新引入总轮数上限。

### 4.3 评分区

- 评估事件到达后立即更新等级、总分、置信度和七维评分。
- 本轮变化的维度短暂高亮，并继续显示确定性的变化解释。
- 流式聊天失败不会回滚已经成功计算和保存的评估。
- 右栏保持次要视觉层级，中间聊天仍是主要操作区。

### 4.4 结束与跳过

- 用户可随时输入“跳过”“结束评估”等明确指令。
- 跳过只结束当前证据链，系统记录其未验证状态并选择下一个高价值问题。
- 结束评估按当前证据生成临时或最终结论，不伪造缺失信息。
- 当程序已找不到有价值的新问题时，AI 提示证据已足以形成当前结论；用户仍可继续补充。

## 5. 系统架构

### 5.1 采用方案

一次用户提交仍由一个客户端请求承载，但服务端内部划分为两个阶段：

1. **结构化评估阶段**：模型提取事实、证据、风险和问题候选；TypeScript 评分引擎应用证据上限、权重、置信度、阈值和否决规则，并按深度设置选定唯一下一问。
2. **对话生成阶段**：服务端把已确定的评估差异、证据缺口、深度设置和唯一下一问交给模型；模型只负责生成自然语言解释，并以指定问题结尾。该调用启用真实流式响应。

这会比单次混合 JSON 流多一次模型生成，但能避免以下冲突：模型在聊天中声称分数变化而规则引擎没有变化、模型追问与程序选题不同、尚未解析完整 JSON 就向用户显示错误结论。

### 5.2 未采用方案

- **单次混合 JSON 流**：请求次数少，但必须边接收边解析未完成的 JSON 字符串，并且模型生成解释时还不知道确定性引擎最终选中的问题，脆弱且容易不一致。
- **先聊天、后台评分**：首字出现更快，但聊天解释和随后出现的评分可能相互矛盾。
- **完整响应后逐字回放**：实现简单，但不是真实模型流，不符合已确认需求。

## 6. 流式协议

`POST /api/analyze` 改为返回 `text/event-stream`。请求体在现有会话和项目数据基础上增加 `interviewDepth: "low" | "medium" | "high"`。

服务端按顺序发送以下语义事件：

- `status`：当前阶段，值为 `assessing` 或 `composing`，只用于明确等待状态。
- `assessment`：完整、已校验的评分快照、证据变更、确定性变化说明和唯一下一问。
- `assistant_delta`：本次 AI 消息新增的文本片段。
- `complete`：完整 AI 消息、消息标识和本轮结束状态。
- `error`：失败阶段、稳定错误码、用户可理解的说明和是否可重试。

接口不得把供应商原始错误体、请求头、API Key 或模型思维过程写入事件。客户端使用流式 `fetch` 读取事件并增量更新 reducer，而不是等待 `response.json()`。

## 7. 状态与持久化

会话状态从单一“提交中”细化为：

```text
idle -> assessing -> composing -> idle
                    -> stopped -> idle
       -> failed ----------------> retry
```

- 用户消息在请求开始前保存，重试时复用同一条消息，避免重复。
- 收到 `assessment` 后，以现有 IndexedDB 事务保存评估、证据和项目状态，再更新右侧 UI。
- `assistant_delta` 只更新内存中的流式草稿。
- 收到 `complete` 后保存完整 AI 消息，并清除流式草稿。
- 对话生成失败但评估已成功时，客户端使用评估事件中的变化说明和唯一下一问补成一条确定性的简短回复，并保存为完整 AI 消息。
- 用户停止生成时保留已经显示的片段；界面补充“已停止生成”状态和确定性下一问，使后续回答仍有明确上下文。
- 评估阶段失败时保留用户输入和上一轮成功评分，允许原地重试。
- 项目新增 `interviewDepth` 字段；旧记录读取时默认迁移为 `medium`。不为该字段增加数据库索引。

过期响应仍需通过项目 id、轮次或请求标识拦截，避免用户切换项目后把流片段写入错误案卷。

## 8. 模型边界

### 8.1 结构化评估调用

- 继续使用严格结构校验和一次格式修复。
- 用户输入始终作为不可信资料隔离，不能覆盖系统评分规则。
- 模型提供事实和候选，不直接决定总分、等级、置信度或最终下一问。
- 证据没有来源或验证方式时，不得从“用户声称”升级为“已验证”。

### 8.2 流式对话调用

服务端提示词必须提供已经确定的评分差异和下一问，并约束模型：

- 使用中文，语气像审慎但愿意协助的尽调访谈员。
- 明确回应用户刚才的内容，不输出泛化套话。
- 解释为什么信息足够或不足，但不虚构证据、不承诺不存在的评分变化。
- 只提出一个问题，并用服务端给定的问题收尾。
- 不输出 JSON、评分规则内部指令、思维过程或第二个备选问题。
- 根据低、中、高深度调整追问细度，但不得自行改变深度。

## 9. 错误处理

- **评估请求失败**：保留用户消息和上一轮评分，在聊天内显示可重试说明，不把整页切换为错误状态。
- **结构校验失败**：服务端执行现有的一次修复；仍失败时返回稳定错误码和可操作说明。
- **评估成功、对话生成失败**：保留新评分，使用本轮确定性变化说明和下一问生成简短后备回复。
- **流中断**：保留已显示片段；若已经收到评估事件，则补充后备回复，否则按评估失败处理。
- **用户停止生成**：中断上游流式请求，不回滚已经保存的评估。
- **IndexedDB 写入失败**：结果仍可查看，但明确标记“尚未保存”并允许重试持久化。
- **项目切换或组件卸载**：取消当前读取并忽略迟到事件。

## 10. 可访问性与响应式行为

- 流式消息容器使用合适的 live region，避免每个 token 都触发干扰性的完整朗读；完成后提供一次稳定消息通知。
- 深度选择器、停止按钮、快捷回答和发送按钮均可通过键盘操作，并有清晰焦点状态。
- 生成结束后焦点回到输入框，不把焦点强制移动到右侧评分。
- `prefers-reduced-motion` 下禁用光标闪烁和评分高亮位移动画，但保留状态文本。
- 窄屏优先显示聊天区，评分和案卷索引延续现有抽屉或折叠策略。

## 11. 测试与验收

实施遵循测试先行：先补充失败测试，再写最小实现。

### 单元测试

- 深度默认值和旧项目回退为 `medium`。
- 低、中、高对同一证据链产生不同的继续追问策略。
- 总轮数不再作为停止条件。
- 确定性选题仍只返回一个问题。
- 对话后备文案正确包含本轮证据影响和唯一下一问。
- SSE 编码与客户端增量解析能处理拆包、合包、多字节中文和错误事件。

### reducer 与组件测试

- `assessment` 事件先更新右侧评分，多个 `assistant_delta` 逐步追加到同一 AI 消息。
- 生成期间禁止重复提交，停止后恢复输入。
- 模糊回答会得到“不足原因 + 一个追问”，不会无依据提高评分。
- 切换问答深度后从下一轮生效，并在刷新后恢复。
- 对话生成失败时保留新评分并呈现后备回复。
- 切换项目后忽略旧流事件。

### API 与浏览器验收

- 使用延迟分块的模型桩证明文字不是等待完整响应后一次显示。
- 真实模型最小调用能够产生多个可见片段，且最终问题与评估事件中的问题完全一致。
- 输入“已有实际订单”时，AI 说明该信息有价值但仍缺少数量、金额、时间或验证依据，并只追问其中最关键的一项。
- 完成一次低、中、高三档会话，验证追问深度差异。
- 验证停止生成、上游超时、结构错误、流中断和刷新恢复。
- 验证现有项目列表、评分、对比和报告流程没有回归。

## 12. 成功标准

本功能只有同时满足以下条件才算完成：

1. 用户始终在同一个输入框中连续交流，不再操作独立追问表单。
2. 模型响应生成时即可见，并且能观察到多个真实流片段。
3. 每轮回复解释本轮证据影响，只包含一个与规则引擎一致的问题。
4. 三档深度行为可区分，默认中档，无总轮数上限。
5. 右侧评分逐轮更新，且模型不能绕过确定性评分规则。
6. 中止和故障不会破坏上一轮数据，也不会让会话无法继续。
7. 自动化检查和一次真实浏览器会话验证均通过。
